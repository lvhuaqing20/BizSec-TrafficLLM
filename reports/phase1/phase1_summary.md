# 阶段1汇报：任务与标签契约

## 一、阶段结论

阶段1已建立三类 Adapter 的任务契约、共享输出 Schema、流水线结果 Schema、数据集任务矩阵和完整标签注册表。原始 `TrafficLLM_Datasets` 未被修改，未执行流量正文到统一样本的转换、模型下载或训练。

本阶段已经进行了标签层数据处理：读取全部样本输出、清洗标签格式、建立标准标签映射、统计分布并审计异常。尚未处理的是 TShark/HTTP/方向序列中的流量内容和协议特征。

当前状态为：**技术校验通过，等待业务语义确认后冻结 v1 契约。**

## 二、完成内容

### 1. 三个任务契约

- Business：输出业务域和业务类型；
- Detection：输出 `is_attack`；
- Attack-Type：仅对攻击样本输出攻击大类和可选家族。

第一版训练目标和推理输出使用相同 Schema，均不包含 `confidence`，只使用明确分类结果。

### 2. 四个 JSON Schema

三个 Adapter 各自定义一个共享输出 Schema，同时用于训练目标和推理输出：

- Business Adapter Output；
- Detection Adapter Output；
- Attack-Type Adapter Output。

完整级联结果另设一个 Pipeline Analysis Result Schema。

Detection 判定为 false 时不调用 Attack-Type Adapter，由编排器生成 `attack_type=benign`。

### 3. 数据集任务矩阵

已明确 11 个数据集变体分别进入哪些任务，并明确以下数据不能自动生成安全标签：

- 应用分类；
- 网站分类；
- Tor 行为分类；
- VPN 应用分类。

### 4. 标签注册表

注册表覆盖全部 290 个声明标签，每个标签记录：

- 原始名称和原始整数 ID；
- 是否出现在 train/test；
- 可参与的任务；
- 对应标准目标；
- 映射依据；
- 是否需要人工审核。

## 六、证据边界

### 解析事实

- 样本数量、标签数量、输出分布和未观测类别来自脚本实际解析；
- 审计结果保存在 `dataset_audit_v1.json`；
- 原始文件标签表哈希保存在 `label_registry_v1.json`。

### 设计决策

- 三个任务的标准输出；
- 哪些数据集进入哪个任务；
- Attack-Type 的大类层级；
- `IRC` 在 Botnet 数据中暂按攻击处理。

设计决策不是原数据直接提供的事实，正式冻结前需要确认。

## 七、需要确认的问题

### Q1：Botnet 数据中的 IRC

当前映射：

```json
{
  "is_attack": true,
  "attack_type": "botnet",
  "attack_family": "IRC"
}
```

原因：原数据将 IRC 与 Neris、RBot、Virut、normal 并列放入 Botnet 检测任务。但 IRC 协议本身不必然恶意，因此注册表标记为 `review_required=true`。

### Q2：跨数据集同义业务标签

v1 暂时不合并，例如：

- `facebook`
- `com.facebook.katana`

后续可以增加独立的 canonical business taxonomy，但不建议在第一版直接合并，以免失去原论文标签可比性。

### Q3：端到端评估边界

原数据不是每条样本都有 Business、Detection、Attack-Type 三类真值。因此：

- 可以训练和评估单个 Adapter；
- 可以运行完整级联；
- 不能对全部样本计算完整三级真值准确率；
- 后续需要单独定义端到端多任务评估子集。
